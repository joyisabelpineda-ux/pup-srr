# Deploying PUP SRR to a public URL

I could not deploy this for you from my environment (no network access and no access to your hosting account),
so **no public URL exists yet**. The only verified address is the local one: `http://127.0.0.1:5000`.
Below is the exact procedure for Render. Everything was tested locally in production mode behind simulated proxy headers
(HTTPS detection, client-IP rate limiting, admin bootstrap, `/healthz`), but not on Render itself.

## Choose a plan (important)

- Render **Free** web services have an ephemeral filesystem and **cannot attach a disk**; a SQLite file there is wiped on restart/redeploy, and the service sleeps after ~15 minutes idle.
- A persistent disk needs a **paid** instance (Starter, about $7/month) plus about $0.25 per GB-month for the disk (1 GB is plenty). Adding a disk means redeploys restart the service briefly and it can only run one instance — fine for SQLite.
  Prices change; confirm at <https://render.com/pricing>.
- A free alternative to explore is a host with a persistent filesystem (for example PythonAnywhere); I have not verified its current terms or prepared a config for it.

## Steps

1. **Create a private Git repository** (GitHub) and push this project. `.gitignore` already excludes `.env`, `instance/`, databases and virtual environments.
   ```
   git init && git add . && git commit -m "PUP SRR" && git branch -M main
   git remote add origin https://github.com/<you>/pup-srr.git && git push -u origin main
   ```
2. In Render: **New → Blueprint**, connect the repository. Render reads `render.yaml` and proposes the `pup-srr` web service with a 1 GB disk at `/var/data`.
3. When prompted for the `sync: false` values, enter:
   - `ADMIN_USER_ID` – e.g. `pup-admin`
   - `ADMIN_EMAIL` – your email
   - `ADMIN_PASSWORD` – a strong password (10+ chars, letters and numbers). It is only used to create the first admin on first start.
   `SECRET_KEY` is generated by Render. `APP_ENV=production` turns on Secure cookies, HSTS and disables demo accounts.
4. Click **Apply**. The build runs `pip install -r requirements.txt`; the start command is
   ```
   waitress-serve --host=0.0.0.0 --port=$PORT --threads=4 --trusted-proxy='*' --trusted-proxy-count=1 \
     --trusted-proxy-headers='x-forwarded-for x-forwarded-proto x-forwarded-host' --clear-untrusted-proxy-headers wsgi:app
   ```
   The `--trusted-proxy…` flags are required so the app sees the real HTTPS scheme and each visitor's IP (otherwise rate limiting would treat everyone as one client).
5. Your public URL will look like `https://pup-srr-xxxx.onrender.com` (shown on the service page). Then optionally set `PUBLIC_BASE_URL` to it so printed QR codes use it.
6. **Verify online** (do not skip): open `/healthz` (should show `{"status":"ok"}`), register a test account, log in, reserve a room, log in as the admin and approve it,
   then in Render click **Manual Deploy → Restart** and confirm the test account and reservation are still there.
7. Make the first admin your own: log in as `ADMIN_USER_ID`, open **Users**, and create/promote additional administrators as needed.

## Operating it

- **Backups:** Render **Shell** → `flask --app wsgi backup-db` writes a consistent copy beside the database; download it or rely on Render's disk snapshots (check their current retention).
- **Closing registration:** set `ALLOW_REGISTRATION=0` and create staff accounts yourself (Shell: `flask --app wsgi create-admin`, or promote from **Users**).
- **Sample data:** `SEED_DEMO=1` creates example campuses/rooms once. Edit/replace them under **Manage rooms**; set `SEED_DEMO=0` before first start to begin empty.
- **Updating:** push to Git; Render redeploys. Schema upgrades run automatically at start and back up the database first.
- **Scaling:** keep a single instance (SQLite + disk). For several instances move to PostgreSQL (not implemented).

## Before sharing widely

HTTPS and Secure cookies are on by default in production, but the app has had no independent security review. There is no email verification or password-reset email,
so a forgotten password is reset by an administrator (**Users → Reset password** shows a one-time temporary password).

## Known limitations

- No email-based self-service password reset (administrators can reset passwords); no SSO/PUP identity verification.
- Door/IoT hardware is not integrated; access results are simulated.
- Free-tier SQLite persistence is not possible on Render (see above).
- Visual layout was written to be responsive but was **not visually inspected in a browser** in my environment; please check it on your devices.

## QR check-in and 15-minute no-show release

- Room QR images use high error correction for improved print/scan tolerance. If an administrator regenerates a room QR code, replace the printed copy because the old token is revoked.
- A successful QR authorization for an active approved reservation records `checked_in_at` and writes audit/access log entries.
- Approved reservations with no recorded check-in are changed to `Cancelled` once their start time is at least 15 minutes in the past. The reservation slot is then available again, and a system audit/access event is recorded.
- This release logic runs when the app receives a request. It is not a background timer, so on an idle service the database update may wait until the next request. Exact release at the deadline requires a separate scheduler/cron job and persistent database storage.
- Schema migration 3 adds `reservations.checked_in_at` automatically on application startup. Existing reservation records are retained by the migration.
